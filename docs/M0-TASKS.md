# docs/M0-TASKS.md — M0 任务单

M0 只有两件事：**冻结契约**、**建起质量工程**。此阶段不放出任何 UI 代码。

下发给执行者时，必须附 `CONTRIBUTING.md` §3 的交付要求与 `docs/TASKS-INJECT.md` 的 worker 注入模板。任务单之外的事一律不做。

依赖关系（无依赖才可并行）：

```
CON-001..006（Tech Lead，已交付草案）
        └── REV-001（独立评审）──┐
                                 ├──> QE-002（conformance harness）──> G0
QE-001（仓库骨架 + CI）──────────┤
QE-003（基准框架 + 数据生成器）───┤
QE-004（密钥扫描器）──────────────┤
QE-005（SBOM/可复现构建）─────────┘
CON-007（schema 双端一致性）依赖 QE-001 的 CI
```

## M0-CON-001　流式事件契约

**目标**：产出 `spec/stream-events.md`，使双端协议层可据此实现出逐字节一致的 `StreamEvent` 序列。

**质量归属**：核心路径（卓越线）——地板表"流式"全部三行 + "一致性"行。

**范围**：允许新建 `spec/stream-events.md`。禁止触碰其他任何路径。

**明确不做**：不写实现代码；不定义 provider 请求侧（属 CON-005）；不定义错误码枚举（属 CON-002）。

**输入依赖**：无（首版）。

**验收标准**：
1. 事件类型闭集且每种都有必填/可选字段表。
2. 存在编号不变量 I1..I12，每条可被 conformance 判定。
3. 五家 provider 各有完整映射表（含失败路径与 off-by-one 风险点）。
4. 取消、重试、终止语义与 ADR-003 无矛盾。
5. 独立评审记录落 `docs/reviews/spec-review-stream-events-1.0.0.md`，零"必须修改"项。

**状态**：草案已交付（1.0.0-draft）。

**DoD**：评审通过 → 版本去 `-draft` → `spec/CHANGELOG.md` 记一条 → 广播。

## M0-CON-002　统一错误模型

**目标**：产出 `spec/errors.md`，使任一失败都能被翻译成"发生了什么 + 可能原因 + 可点操作"，且双端同码同义。

**质量归属**：核心路径（错误可自救）。

**范围**：允许新建 `spec/errors.md`。

**明确不做**：不定义 UI 布局；不定义重试退避实现（属 ADR-003）；不写文案资源文件。

**输入依赖**：ADR-003（取消语义）。

**验收标准**：
1. 错误对象字段表完整，含 `raw` 的 512 字节与脱敏约束。
2. code 闭集，每个 code 至少 1 条原因 + 1 条 action。
3. 四家 provider 的状态码/错误类型映射表完整。
4. 脱敏规则可被机器测试（测试向量文件要求写清）。
5. 文案硬约束（长度、禁语）明确。

**状态**：草案已交付。

## M0-CON-003　数据库 DDL 与导出 Schema

**目标**：产出 `spec/schema/v1.sql`、`spec/schema/export-v1.json`、`spec/schema/export-v1.notes.md`，使双端可建出同构数据库并做无损往返。

**质量归属**：核心路径（数据完整性，一票否决）。

**范围**：允许新建上述三个文件。

**明确不做**：不写迁移脚本（M2 起）；不实现导出代码。

**输入依赖**：无。

**验收标准**：
1. `v1.sql` 在 SQLite 3.40+ 上 `executescript` 零错误，`foreign_key_check` 为空（已实测：28 个对象 / 12 索引）。
2. 每个实体含 `sync_version / rev / origin_device`（同步预留）。
3. 软删除 + 回收站 + 附件引用计数的语义有明确文字。
4. 导出 Schema 通过 JSON Schema 2020-12 自校验（已实测可解析，28 个 $defs）。
5. "无损"的判据写成可执行断言（export-v1.notes §2）。

**状态**：草案已交付。

## M0-QE-001　仓库骨架与 CI

**泳道**：质量工程｜**依赖**：D5（远程仓库）｜**预估**：1 个工作单元

**目标**：建立双端空工程 + CI，使任意 PR 上能自动跑 lint / 单测 / 架构测试 / 许可证检查 / schema 一致性，且全部为绿。

**质量归属**：非核心（地板），但它是所有 Gate 的证据来源，未通过则后续全部阻塞。

**范围**：
- 允许新建：`androidApp/`（空 Compose 工程 + detekt + explicitApi + 架构测试骨架）、`windowsApp/`（空 WinUI 3 工程 + TreatWarningsAsErrors + analyzers + 架构测试骨架）、`ci/`、`.github/workflows/`、`.editorconfig`、`.gitignore`、根 `build.gradle.kts` 等构建文件。
- 禁止触碰：`spec/**`、`docs/**`。

**明确不做**：不实现任何业务代码；不加除构建必需之外的依赖；不配置签名/发布。

**输入依赖**：ADR-001（技术栈）、`spec/schema/v1.sql`。

**验收标准**：
1. `./gradlew detekt test` 与 `dotnet build /warnaserror` 在 CI 上通过，输出零警告。
2. 架构测试存在且能对一次故意违规（领域层引用 UI 类型）报失败——需附该负向测试的原文输出。
3. schema 一致性检查：Room 导出的 schema JSON 与 `v1.sql` 归一化后逐句比对，差异为 0（此检查可先 skip 但必须有失败用例证明它会失败）。
4. 许可证白名单检查接入（初始白名单由 D6 决策提供）。
5. 包体检查步骤存在（当前只记录基线数字，不设门）。

**工件**：CI 运行原文（三个 job 全绿）、负向测试失败输出、schema diff 输出。

## M0-QE-002　Conformance Runner 与样本生成器

**泳道**：质量工程｜**依赖**：CON-006、REV-001｜**预估**：2 个工作单元

**目标**：实现 `tools/conformance/`：能按 `meta.json` 的 `chunk_pattern` 把样本字节切片喂入任一端的协议层，输出规范化的 `events.jsonl`，并对双端结果做 SHA-256 比对。

**质量归属**：核心路径。

**范围**：
- 允许新建：`tools/conformance/`（生成器、runner、比对器）、`spec/conformance/samples/`（生成出的样本字节）、`spec/conformance/redaction-vectors.jsonl`。
- 允许新建测试：`tools/conformance/tests/`。
- 禁止触碰：`spec/*.md`（CASES.md 除外，只允许追加"已生成"标记）。

**明确不做**：不实现双端协议层（M1 才做，runner 先用一个"桩实现"完成端到端验证）；不做性能测量。

**输入依赖**：`spec/conformance/CASES.md` 全部 70 用例。

**验收标准**：
1. 70 个样本目录全部生成，每个含 `stream.sse` 与 `meta.json`。
2. 生成器可复现：同一 seed 两次运行产出字节 SHA-256 相同（附两次运行输出）。
3. Runner 对一个故意错误的桩实现报失败（负向验证，附输出）。
4. `events.jsonl` 规范化（键排序、无空白、UTF-8 无 BOM）。
5. `redaction-vectors.jsonl` ≥40 组，覆盖 errors.md §7 每条规则。

**工件**：生成器两次运行输出、负向测试输出、样本清单（70 行）。

## M0-QE-003　基准框架与合成数据生成器

**泳道**：质量工程｜**依赖**：无（与 QE-002 并行）｜**预估**：2 个工作单元

**目标**：实现"能被重复执行、原始数据可归档"的测量框架，以及 1000 条 / 10 万条消息的合成数据生成器。

**质量归属**：核心路径（没有它，所有性能数字都只能靠嘴说）。

**范围**：允许新建 `bench/`（`common/`、`android/`、`windows/`）、`bench/render-goldens/`（空目录 + README）。

**明确不做**：不写被测业务代码；不做真实网络测量（用本地 mock server）；不建看板。

**输入依赖**：`docs/benchmarks/README.md`（测量方案）、CON-004 的 20 组用例。

**验收标准**：
1. 每个指标有可执行测量入口，输出 JSONL 原始样本（含 timestamp、value、unit、build_id、device）。
2. 汇总器能从 JSONL 算出 min/p50/p95/p99/max 并生成 markdown 表（附一次真实运行的表）。
3. 合成数据生成器：seed 固定 → 产出 1000 会话 / 10 万消息 / 附件引用 / 分支树，重复运行字节一致。
4. mock server 能模拟 SSE 流（含可配置延迟与 chunk 大小）。
5. 文档说明"怎么跑"与"日志放哪"，不超过 60 行。

**工件**：一次真实运行的 JSONL + 汇总表 + 脚本路径 + 生成器两次运行的一致性证明。

## M0-QE-004　密钥明文扫描器

**泳道**：质量工程｜**依赖**：无｜**预估**：1 个工作单元

**目标**：实现 `tools/secret-scan/`，覆盖 ADR-002 §5 的全部范围与规则，能在 CI 与 Gate 前独立运行。

**质量归属**：核心路径（一票否决项）。

**范围**：允许新建 `tools/secret-scan/`、`docs/security/README.md`。

**明确不做**：不接入外部 SaaS 扫描服务（数据不出本机）。

**验收标准**：
1. 规则：熵扫描 + 5 类前缀 + 已知测试密钥精确匹配 + 通用高熵串。

## M0-QE-005　SBOM、许可证与可复现构建

**泳道**：质量工程｜**依赖**：QE-001｜**预估**：1 个工作单元

**目标**：任意提交都能产出 SBOM 与许可证清单，且同 commit 同产物的哈希稳定（或明确记录不可复现的原因）。

**质量归属**：非核心（地板）+ 合规必做。

**范围**：允许新建 `ci/sbom`、`ci/license`、`docs/security/`（报告）。

**明确不做**：不配签名证书；不做发布流水线。

**验收标准**：
1. Android：`cyclonedx` 或等价产出 `bom.json`；Windows：`dotnet list package --include-transitive` 转 SPDX。
2. 许可证白名单校验：命中黑名单即 CI 失败（附一次故意引入 GPL 依赖的失败输出）。
3. 可复现性：同 commit 连续两次构建，Android APK 与 Windows 单文件产物的哈希相同，或给出逐项不可复现原因清单。

**工件**：两份 SBOM 样例、黑名单失败输出、两次构建哈希对照。

## M0-CON-007　Schema 双端一致性校验

**泳道**：契约（Tech Lead）+ 质量工程执行｜**依赖**：QE-001｜**预估**：0.5 个工作单元

**目标**：把"Room 生成的 DDL 与 `v1.sql` 等价"变成 CI 可判定的检查，防止 Android 与 Windows 的库结构漂移。

**质量归属**：核心路径（数据完整性）。

**范围**：允许修改 `ci/`、`tools/schema-diff/`、`androidApp/` 的 Room schema 导出配置。

**明确不做**：不改 `v1.sql`（如需改，走 spec 变更流程）。

**验收标准**：
1. 归一化规则明确（去注释、统一大小写、统一空格、列序比较方式）。
2. 对故意改动一列类型的 Room 实体能报出差异（附负向输出）。
3. 差异报告定位到表与列，不是"整体不一致"。

**工件**：负向差异输出、正向通过的 CI 日志。
